# 单店全量重构：数据迁移、解耦与性能评估

更新日期：2026-11-20。**采用独立新库开账，所有使用端一次切换。v2 候选可进入隔离验收，尚不得正式发布或切换营业。** 网页收银、商家后台、Android 和天猫精灵已接 v2，旧资金入口已从候选移除。文件 SQLite、真实 PostgreSQL、本机只读 HTTPS 演练和隔离 Chromium UI/API 冒烟已验证关系账务、权限、原号重试、换代和恢复；浏览器冒烟只覆盖合成会员登录、查找、档案和充值，不替代目标服务端浏览器验收。生产库、营业手机和真实会员数据均未操作。候选源码与证据见 [实施台账](refactor-implementation.md)。

## 2. 风险结论的变化

此前的大部分迁移复杂度来自“持续营业、多店、保留全部历史、兼容长期离线旧设备”。这些不再是本次约束。建议采用“最终备份 → 最小数据投影 → 新库期初导入 → 全面切换”，不实施长期双写或旧协议适配。

| 风险项 | 新边界下的判断 | 仍需满足的条件 |
| --- | --- | --- |
| 91 人静态资料和余额导入 | 相比全历史迁移，风险显著下降 | 完整备份、逐人比对、精确金额、重复导入不重复加款 |
| 丢弃旧流水和旧累计数 | 用户已接受的信息取舍 | 新系统明确期初与切换日期；不能仍展示虚假的全历史累计 |
| 新旧同时写入 | 可以通过一次性停旧解决 | 旧 API、网页、设备全部停用，旧会话/旧写路径失效 |
| 新资金核心正确性 | 仍是中高关注项 | 余额、流水、幂等和审计原子性及随机/并发测试 |
| 手机 SQLite 与离线同步 | 仍是中高关注项 | 持久化完成再报成功，异常重试不重记，冲突不静默覆盖 |
| 代码解耦与性能 | 不会因数据少而自动完成 | 模块依赖检查、查询与并发实测、增长数据压测 |
| 回滚 | 上线前简单，开业后需要专门设计 | 新交易必须保留；禁止用旧备份覆盖开业后账目 |

这些是定性评估，不是事故概率。可以在当前规模下用更简单的切换方案完成彻底改造，但不能据此承诺重写交易系统天然低风险或绝无缺陷。

## 3. “全部入 SQL”和“不存服务器本地”的明确含义

| 位置 | 目标职责 | 约束 |
| --- | --- | --- |
| 独立/托管 PostgreSQL | 在线会员、资金、流水、配置、身份、权限、许可、操作回执和审计 | 业务实体拆成关系记录，主外键、唯一约束、索引和事务维护一致性 |
| API 服务实例 | 鉴权、应用服务、SQL 访问与受限临时计算 | 不保存会员 JSON、业务 SQLite、账本备份或长久本地文件缓存；可重建、可替换实例 |
| Android 手机 SQLite | 手机离线会员、账户、流水、配置和同步 outbox | 使用真实数据库事务；禁止 localStorage 数组、JSON 字符串或单个 BLOB 伪装关系存储 |
| 手机安全存储 | 登录凭据、许可验签相关安全状态和密钥保护 | 使用 Keystore 等安全机制；不将密钥或明文密码混入普通业务表 |
| 在线浏览器 | 在线页面和短期视图 | 不持久保存整份会员/余额；必要凭据和结果未明请求标识属于受控恢复元数据 |
| 备份 | 用户主动导出或数据库备份系统 | 位于明确的独立备份位置；API 不在本机自动积累业务备份副本 |
| 安装包和部署配置 | 发布物、证书、密钥挂载等系统材料 | 与业务数据库区分，访问受控，不宣称应用服务器绝无任何文件 |

SQL 是访问与建模方式，数据库仍需物理存储。当前 Compose 不运行或挂载 PostgreSQL 数据库；迁移、应用和可选恢复身份连接独立数据库主机或托管服务。同机跑测试库只用于验证，不能代替目标部署拓扑。

JSON 可用于接口传输和一次性旧备份读取；新运行态不再持久化整店 JSON 账本，不将会员、交易集合或配置对象改名后塞入 JSON/TEXT/BLOB。签名和加密材料是安全载荷，不能用来隐藏业务快照。审计使用明确事件字段和关联记录，诊断只存必要、去敏后的结构字段。

不可变的单命令/单任务回执可保存当次响应结果，供同一请求去重和恢复；不能以回执装载当前资料、配置、经营报表或回放业务。PG 的结果列使用 JSONB，当前业务事实仍从明确关系表读取；SQLite 的任务结果另拆关系行。这不是整店 JSON 事实源或 ARC-05 的豁免。

金额统一为分：SQL 使用有符号 BIGINT，领域使用精确整数；SQL 列命名为 *_cents，新协议对应字段以 *Cents 命名并用十进制整数字符串传输，避免 BigInt 的 JSON 序列化和大数精度问题。展示为元时做精确格式化，不通过浮点数回写资金。

## 4. 91 位会员的最小迁移合同

### 4.1 字段与来源

| 字段 | 处理规则 |
| --- | --- |
| 原会员 ID | 来源有 ID 则保留，作为导入映射键；姓名和电话都不能替代身份 |
| 姓名 | 原文核对；空姓名阻止正式导入并给出行号 |
| 电话 | 可空，保留前导零与原显示文本；规范化号码另列用于查询与校验，不按号码自动合并 |
| 必要备注、现有标签 | 默认作为关键档案一并保留；仅迁移源中实际存在的信息，不新增采集个人资料 |
| 剩余余额 | 有符号整数分；逐人精确一致；缺失、非数值、超范围必须拒绝，不能当 0 |
| 注册时间 | 新库用导入时间和期初批次标记来源，旧注册时间不进入本次最小投影；导入不计作新客 |
| 旧归档状态 | 预检列出；91 人最终清单内每人均有明确去向，不能默认过滤后少导 |
| 其他历史字段 | 不进入新业务事实源；旧流水、旧累计与旧同步状态不迁移 |

优先从旧版完整 JSON 备份提取 members 中的上述字段，仅作为一次性离线转换输入；运行态不继续提供旧快照恢复/旧账本回放。转换工具隔离于新业务代码，导入后可独立移除。

旧 JSON 中余额单位为分，不得再乘 100；Excel 中余额列为元，按精确十进制换算，不能混用。现有 Excel 导出把余额列称为“卡内本金余额(元)”，但旧余额包含充值赠送，迁移语义必须是“剩余可用余额”，不能误解释成纯实收本金。若使用表格而缺少原 ID，须在预检阶段产生稳定行映射并人工核对，不能在每次重试时随机生成新身份。

### 4.2 期初余额，不冒充充值

新库建立独立 account_openings 期初记录，允许正数、零和负数，记录导入批次、来源摘要和确认时间。

- 初始 balance_cents = opening_balance_cents。
- 切换后的 balance_cents = opening_balance_cents + 全部新流水 delta_cents 之和。
- 本期新充值、本期新消费等累计从 0 开始；它们与期初余额分开。
- 旧 total_recharge / total_consume 不迁移，不再强套旧版“余额 = 旧累计充值 − 旧累计消费”的校验。
- “期初结转”可以作为展示项目，但不计入今日充值、现金收入、活动赠送、新客或营业额。
- 旧期初没有可供新系统撤销的充值原单；不能用“撤销充值”冲掉期初。开业后确需更正必须走有权限、有原因、可追溯的更正流程。
- 剩余余额不再尝试拆成剩余实收本金和剩余赠送额度；源数据不足时不能凭估算拆分。新交易单独记录实收与赠送。

### 4.3 导入的验收与幂等

1. 生成候选清单，只读预检，确认记录数恰为 91；如果源数据不是 91，出具差异并阻止正式导入，不截断、不补造。
2. 核对每人的姓名、电话、原 ID 和余额，并分别统计正储值、负欠款、零余额人数；净额相同不足以证明正确。
3. 同一店铺、同一来源摘要/导入批次重复提交，只返回原结果，不新增会员、不再次增加余额。
4. 本次 91 人导入使用一个数据库事务，任意一人失败则全部回滚；导入完成后锁定该期初批次，禁止向已营业账本追加同一份期初。
5. 在新库中逐人核验后，再下载到新手机 SQLite 核验；手机重启、断网再打开，记录数与余额仍一致。
6. 正式导入状态和审计进入 SQL；成员明文、完整备份和授权密钥不得进入仓库、测试报告或应用日志。

## 5. 必须完成的解耦

采用模块化单体，在线资金仍在同一个 PostgreSQL 事务内；不为解耦引入不必要的跨库事务和微服务运维。

| 模块 | 职责与建议关系实体 | 不允许的依赖 |
| --- | --- | --- |
| 领域计算 | 金额、期初、消费、充值、冲正、欠款和版本规则 | 不依赖 Vue、DOM、localStorage、HTTP、pg 或 Android 桥 |
| 应用服务 | 资金命令、权限、幂等、事务和审计协调 | 不把余额写入散落在控制器/组件中 |
| 会员档案 | members、member_tags、档案版本 | 不直接修改资金账户或交易原单 |
| 资金 | member_accounts、account_openings、ledger_entries、reversal_links | 不读取或保存整店快照 |
| 销售与规则 | recharge_details、payment_records、consumption_items、services、plans/settings | 规则变化不改写历史成交金额 |
| 同步与恢复 | command_receipts、sync_changes、sync_outbox、import_batches | 不导入旧 replayOperation 或旧 v1 快照恢复逻辑 |
| 平台与身份 | 用户/角色/权限/设备/在线及离线许可 | 平台身份、商家身份、本地身份保持明确边界 |
| 查询与报表 | SQL 分页、过滤、聚合及可重建汇总 | 不依赖 UI 当前加载的会员/流水全集 |
| 诊断与审计 | 核心审计同事务；诊断有界异步并落受控 SQL | 不将网络日志服务故障引入资金提交；不丢弃核心资金审计 |
| 存储适配器 | PostgreSQL、Android SQLite 各自实现接口与事务 | 服务端不再导入客户端存储引擎；不以后台异步写包装同步保存接口 |

复合业务键和外键包含 store_id；虽然当前只有一家店，也不能省略租户隔离。保留未来扩展边界，但当前不建设分库分片或集群。

交付时须移除旧 accounts.data 财务路径、旧 localStorage 账本、旧全店摘要与旧回放依赖；对仍需要的安全规则重写并测试，而不是以“不保留旧逻辑”为由移除幂等、权限或冲正保护。

## 6. 必须完成的性能优化

1. 写入按账户和交易粒度进行。资金事务只访问目标会员、必要规则、收据和审计，禁止每笔交易重新加载/序列化/校验整店账本。
2. 使用账户版本与短行锁处理同会员并发。不同会员不因一个整店 expectedRevision 冲突而互相阻塞业务；如同步提交水位需要短暂协调，必须单独测量并缩短该临界区。
3. 会员、流水、审计提供服务端分页、明确排序和有上限的查询；大页不用无限 OFFSET 扫描，热点路径按实际查询建立复合索引。
4. 新同步协议按变更游标/实体版本拉取增量，支持删除/归档标记、分页、去重与过期游标重建。水位必须与提交顺序相容，不能简单拿 sequence 分配值当完整提交顺序。
5. 报表由数据库聚合；页面筛选不能改变报表统计全集。汇总可异步重建，但资金确认、权限检查、幂等读取留在主写库。
6. 不在数据库事务中等待外部语音、远程日志或其他慢网络；连接池、请求体、队列和并发都有上限。
7. SQLite 访问离开 UI 热路径，正确处理忙等待、事务、外键和提交失败；不为省等待而先报成功再异步落盘。
8. 输出可重现的查询计划、延迟、吞吐、锁等待、内存和长期运行报告。91 人正常不代表数据增长后自动合格；测试数据必须扩展到大规模。
9. 长日期流水交给有界异步 XLSX 任务，取同一 SQL 快照，独立线程编码。核对导出与正常收银同跑的资源和延迟，按 [专项容量门槛](refactor-test-plan.md#7-性能与容量验收) 验收。

性能是本次完成条件，不推迟到“以后再优化”。具体数据集、负载与暂定验收预算见 [专项测试计划](refactor-test-plan.md)。

## 7. 新离线模式与数据权威

- 云端绑定模式：PostgreSQL 是已接受交易的权威；手机 SQLite 保存副本、本地待提交交易和 outbox。离线时本机余额需明确待同步状态，同步冲突保留原单并提示核对，不静默覆盖。
- 独立离线许可模式：手机 SQLite 是该离线账本的权威，许可公钥验签与本地登录照常执行；不默认上传到云端。切换为云端模式须显式导出/核对和建立归属，不能混用两份资金事实。
- 当前默认只指定一台设备承担离线资金写入；多设备在线或恢复联网仍可能与离线变更竞争。用账户版本和冲突策略保证不丢单、不重复；不承诺断网时跨设备余额实时一致。
- 浏览器保持在线业务模式；结果未明请求按原命令号查询/重试，刷新或重登不能制造新的一笔交易。
- 手机卸载和清数据会移除本地账本及未同步数据，备份必须位于应用私有目录之外并确认可独立读取。断网场景不能依赖“稍后从服务器找回”尚未上传的交易。

## 8. 一次性切换流程

| 顺序 | 负责人 | 动作与放行条件 |
| --- | --- | --- |
| 1. 锁定并验收候选 | 开发、测试、运维 | 固定源码、镜像、正式签名 APK 版本和摘要。先通过 [目标服务与签名真机验收](refactor-test-plan.md#10-发布清单与完成状态)，用合成 91 人演完备份、期初、同步、断网和带新增交易的恢复。签收后才确定真实开账的维护窗口。 |
| 2. 停旧账 | 店主、运维 | 确认维护窗口；锁定旧网页/API/设备/语音所有写入口，逐台核对原待办。记录最后一笔旧交易、切换时间、来源水位与未处理项；待办未核清则继续停写。 |
| 3. 取得最终来源 | 店主、运维 | 从包含最后一笔的权威旧账导出完整备份；在应用外两个独立位置保存，分别重新打开并读回，核对字节 SHA-256 和内容。用离线转换工具生成期初候选，另核对原始来源摘要、期初内容摘要、91 人原 ID、关键资料与逐人余额。正余额、负欠款、净额、零与欠款人数分别核对。任何差异先查原因。 |
| 4. 开新账 | 运维、店主 | 使用独立 PostgreSQL 的新空库；初始化权限、账号、授权与业务配置。云端绑定模式由店主在后台导入一次，获原批次回执后逐人复核数据库与报表；未确认时只用原批次和原文件查回执。独立离线门店只在 SQLite 导入一次，不能把它当云端期初再导入。 |
| 5. 换手机及入口 | 店主、运维 | 两份旧备份与新库核对签收后，才可重装设备；用已验收签名 APK，在正确门店和账号下加载云端副本或导入独立离线期初。逐人核对人数、金额及待办，重启及断网重开后再核验。不启用旧服务、旧设备或旧令牌。 |
| 6. 恢复营业 | 店主签收，运维执行 | 实际账本只读检查期初未入营业报表、授权及当前代际；测试交易和冲正在隔离演练库完成。书面记录放行时刻与统计起点，开放新版唯一写入口，核对第一笔真实交易、原单号及同步结果并开启新版备份。 |

验收单记录候选摘要、原账最后一笔、两份备份位置与读回摘要、批次号及两份输入摘要、导入回执、逐人签收结果、手机与账本代际、操作者和时间。手机号、余额明细与原备份只存受控位置；实施台账只记录证据编号和结论。任何一项失败时停在当前步骤，其中云端导入失败不提前卸载旧手机。

## 9. 回退与安全删除边界

| 时点 | 可采取的方案 |
| --- | --- |
| 新版尚未正式产生业务交易 | 保持停业，修复新版并重新初始化；必要时用已核验备份临时恢复旧版使用，但不在新代码内保留旧实现 |
| 新版已经产生交易 | 优先修复新版，或在停写后完整保留新交易、收据及设备待办再执行经验证的恢复；不能直接覆盖回旧期初 |
| 旧手机尚未卸载 | 先验证外部备份与新库期初，再卸载；不能把应用缓存文件当作独立备份 |
| 计划删除旧服务器业务数据 | 确认数据库目标、可恢复副本和新库验收均完成后，在实际部署步骤中执行；本轮不操作删除 |

历史可以舍弃，但从新版开始的新流水、回执、审计不能继续随意删，否则新的资金核验基础也会消失。

同一门店恢复后也不是原账本的无缝延续：恢复事务必须创建新 ledgerEpoch，保留历史回执的原代际，阻断旧设备的待办和游标。已实现的协议会拒绝代际缺失/不符或对历史回执自动换绑；不能仅回滚数据、保留旧代际就恢复营业。跨代际待办由原账号/设备在本机逐笔核对，写出并读回外部原单、记录结论后才允许店主重建副本。找不到同代际原回执、同代际水位倒退或账号无法还原时，停止在受影响设备记账并交由运维核对；详见 [原单处置](refactor-implementation.md#原单与恢复处置)。云端完整恢复代码已测，目标环境恢复演练仍是放行条件。

## 10. 完成定义与测试状态

重构完成必须同时满足：

- 91 位真实会员关键资料与余额逐人核对通过，零/负余额和重复导入正确。
- PostgreSQL 与手机 SQLite 关系化落地，API 无本地业务文件依赖；新运行态无旧快照或回放路径。
- 解耦依赖检查、查询计划、分页与增量同步、不同会员并发、压力与长期稳定性全部达到门槛。
- 资金逻辑、批量、属性/随机、幂等、权限、安全、故障、备份恢复、Android 真机与更新安装流程测试通过。
- 保留此前要求的登录/平台后台/商业授权/离线使用，以及会员、充值、消费、撤销、欠款、报表、搜索/提醒和更新等功能；不是仅交付一个新数据表。
- 核心用例不得以 skip 或“以后补测”视为通过；构建成功不能替代原生和真实数据库测试。

当前候选在本机为合成 91 人开账、写新账，经过受限角色、只读 HTTPS 读回归档、恢复并逐人对账；重复恢复上传的连接提前关闭问题已定位并修复。锁定交付包在干净 Ubuntu 24.04/WSL2 环境完成 Linux deployment 回归 17/17，关闭了共享 Windows 依赖目录导致的构建环境缺包项；Windows 全量套件仍有平台不支持的 `flock` 一项跳过，其对应 WSL 单项已通过。上一版 `f74a8f2` 的真实 PostgreSQL 10 万笔、100 万笔归档恢复及 20 店基线隔离均通过，百万笔正式恢复 316.53 秒，保留原 SQL 与归档时限；本轮归档服务和数据库实现未变，按范围保留这些报告及原摘要，不能写成当前候选重新跑过百万笔。增长演练已修复账户版本文本排序、整店反复扫描和预览回滚后外键误选索引；更早的 387.88 秒记录只作历史对照。[实施台账](refactor-implementation.md)区分当前实测、未变实现的范围证据、历史失败及剩余发布门槛。按目标服务与正式 APK 真机并行验收、真实开账串行执行的顺序推进。

## 11. 实施顺序与交付物

1. **候选已接通：** 领域规则、关系 schema、新 API、界面、备份恢复、语音、旧路径清理已进入同一工作区；代码与部署依赖审计通过。
