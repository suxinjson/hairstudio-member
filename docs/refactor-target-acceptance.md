## 目标服务：依次执行

| 检查 | 实际执行与留证 | 失败停在哪里 |
| --- | --- | --- |
| REF-01 部署与隔离 | 用 `docker compose ps -a` 核对迁移成功退出、API 和代理就绪。代理验证 TLS、健康/就绪及三个页面。用 `docker inspect` 核对 API 容器 `ReadonlyRootfs`、实际可写挂载及镜像 ID；核对外部库地址和各角色权限，包括普通身份不能调用统计函数、恢复身份仅能执行固定函数且无 MAINTAIN。证明写根文件系统被拒绝、API 没挂业务数据卷，外部不能直连 API 或 PG。 | 角色越权、错误 TLS、错误数据库或非只读运行，先修正环境。 |
| REF-02 真实 HTTPS 合成小样本 | 用合成 91 人跑期初预览、提交、原号重试、金额及报表核对。新增充值、消费、冲正后，经代理导出归档并从应用外重新读取。第二套隔离 PG 准备同店空目标，经代理预览回滚再恢复；逐人核对，验旧代际拒绝、原恢复号不会覆盖新交易。并验会员与异步流水 XLSX 下载、取消、过期和权限变化。由真实 Chromium 浏览器打开隔离 HTTPS，记录浏览器/OS 版本、候选摘要与脱敏证据，逐步验证三个入口加载、会话建立与退出、会员查找、充值/消费确认与结果未明时原号恢复、角色拒绝、报表和 XLSX 下载；写入前后均核对隔离账本。 | 任一人数、资金、回执、文件、权限或页面交互结果不一致，记录原号、代际和摘要，保留现场。 |
| REF-03 性能与正确性 | 独立施压端通过正式 HTTPS 代理，用专用账号调用真实 API；按 [并发矩阵](refactor-test-plan.md#6-真实并发与幂等) 和 [性能预算](refactor-test-plan.md#7-性能与容量验收) 执行。D1 预热后 20 RPS × 30 分钟，再跑 40/100 RPS 各 5 分钟、降压恢复、4 小时长测，同跑异步导出；独立运行 D2/D3。保存查询计划、API/PG 资源曲线、实际成功/拒绝/漏发和资金对账结果。 | 资金错误、跨店数据、非预期 5xx、未达到稳态预算或超 60 秒仍未恢复则不签收。 |
| REF-04 故障与安全 | 在完成备份读回的可丢弃环境注入 API 重启、数据库断连/重启、事务超时和磁盘故障，核对原号查回、历史不变、连接释放与继续营业；按 [安全矩阵](refactor-test-plan.md#8-安全与滥用测试) 验身份、过期、跨租户、部署权限、Web、依赖和发布物。记录实际恢复耗时及漏账量。 | 有半账、不可恢复、权限绕过或未处置严重问题则不签收。 |

目标施压端不在 API 进程或数据库主机内，不走调试鉴权。容量与增长归档使用同一套能通过生产代码完整校验的合成事实。负载报告只计实际成功请求；分别保留冲突、限流、繁忙、超时和未发出的数量。

### REF-03 独立施压步骤

1. 给 D1、D2、D3 各准备一个新迁移且可丢弃的隔离库，库名为 `member_refqa_<tag>`，`tag` 只用 6–24 个小写字母或数字。用迁移身份运行 [合成样本生成工具](../acceptance/reference-fixtures.mjs)：D1 生成 1 店、1,000 人和 10 万流水，D2 生成 1 店、10,000 人和 100 万，D3 生成 20 店各 500 人和 1 万流水。工具拒绝已存在门店或发布记录的库，同时生成完整成交、原回执、同步和审计。输出报告保留源摘要与账本期次，凭据仅注入环境；生成后由正常应用账号访问。测试期间保持这些门店独占，其他测试不要同时写入。
2. 从生成报告提取 `plan` 对象到受控目录，按[计划示例](../acceptance/reference-load-plan.example.json)替换隔离 HTTPS 入口并填写来源地址。手工准备冒烟数据时，门店名、用户名和会员编号/姓名使用同一 `refqa-<tag>-<两位门店编号>` 前缀；财务写入为每次 2 分且无赠送。时间用 UTC ISO 格式，`fixtureFrom` 覆盖合成流水，`fixtureTo` 至少比启动时间晚 5 小时。密码按 `passwordEnv` 名称注入；HTTPS 可用 `NODE_EXTRA_CA_CERTS` 信任内部 CA。保持证书校验和生产限流开启。
3. 先用 `smoke` 验一店一账号。正式负载在 `clients` 配置至少 12 组，并为每组填写属于施压机的 `sourceAddress`。生产限额为每个代理所见来源 180 次/分钟，每会话 120 次/分钟，每账号写入 30 次/分钟。建议 D1/D2 用 16 组账号均摊到 8 个实际来源，D3 用 20 组均摊到 10 个实际来源并覆盖所有门店。先从代理日志确认确实看到了各个来源；若经 NAT 后仍是一个地址，单出口最多约 3 RPS，不能签收 20 RPS 稳态。
4. 分别准备 `steady`、`burst40`、`burst100`、`soak`、`d2`、`d3` 计划并顺序执行。驱动对每个阶段保存计划、成功、限流、繁忙、超时与漏发，保存写入原号并分别核对每个写入账户和门店汇总。`pass-workload` 只代表该计划的 HTTP 负载和对账通过；查询计划、资源、热点并发、同跑导出与故障验收仍须独立留证。
5. 增长归档从实际代理出口下载。独立读回后，在第二个同店空库按顺序执行预览、确认恢复、逐户金额及版本对账、旧代际拒绝、记新账、用原恢复号重试。分别记录导出、读回、预览和提交的时长，以及同时收银时的错误和资源。不临时抬高 SQL 或归档时限掩盖超时；D3 记录实际恢复了哪些门店，并覆盖其他门店不受影响。

~~~sh
MEMBER_REFERENCE_FIXTURE_DISPOSABLE=1 node acceptance/reference-fixtures.mjs qa123456 d1 > /secure/qa123456-fixture.json
MEMBER_REFERENCE_LOAD_ISOLATED=1 node acceptance/reference-load.mjs /secure/steady.json
~~~

生成前从秘密管理器注入 `MEMBER_REFERENCE_FIXTURE_DATABASE_URL`（显式主机、端口和库名，URL 不加查询参数）和专用的 `MEMBER_REF_PASSWORD_FIXTURE`。外部 PostgreSQL 强制验证 TLS；私有 CA 用 `MEMBER_REFERENCE_FIXTURE_CA_FILE` 指向 CA 文件。归档恢复到另一个已准备同店 ID 的空库，以应用导出文件为输入，先预览回滚再提交和逐户复核。

执行目录下的 `output/refactor-v2/reference-load/` 保存 `summary.json`、`timeline.ndjson` 与 `write-originals.ndjson`。保留各次运行的工具 SHA-256 与候选摘要，本机 Caddy/真实 PG 的驱动冒烟结果见[实施台账](refactor-implementation.md#验证命令与当前证据)。

在开发机可先用 `node acceptance/reference-fixtures.verify.mjs d1 roundtrip` 预演，替换为 `d2` 或 `d3` 切换样本。该命令只接受显式标记的本机专用 `member_relational_test`，创建并清理独立样本库；`baseline` 只做基线，`roundtrip` 还做归档及恢复。D3 核对全部 20 店基线和跨店隔离，恢复选第一店。此工具直调应用服务，目标验收仍经正式代理和受限账号。

## 签收与交付

测试和运维在每项报告记录 `候选 SHA-256 / 产物标识 / 环境 / 检查编号 / 时间段 / 预期 / 实际 / 结论 / 证据 / 签收人`。未实跑记为“未验证”，失败修复后保留原证据并复测受影响项。可复制 [受控验收记录模板](refactor-acceptance-record-template.md)。目标服务与正式真机都签收后，店主安排停写并把真实期初逐人核对结果、两份备份读回摘要和最后旧单记录到受控业务验收单。

可复制 [隔离验收与开账记录模板](refactor-acceptance-record-template.md)。目标环境运行记录与营业开账记录应分开保存；模板只留在受控存储，报告和仓库不得包含连接密码、签名私钥、真实会员明细或原始备份。隔离阶段所有签收字段初始为“未验证”，完成后附具可复查的证据路径和责任人。
