# v2 平台与账本架构

当前候选已接入 v2，尚未发布。数据迁移和放行按 [单店重构评估](relational-refactor-assessment.md) 与 [测试门槛](refactor-test-plan.md)，实际证据见 [实施台账](refactor-implementation.md)。

## 实施范围与边界

已有平台改造把平台控制面、门店业务面和原生离线运行分开。平台管理员身份不属于任何门店，门店店主不能成为平台管理员，也不能修改商业授权。首次使用必须在线登录，或导入有效的离线设备授权并设置本地登录密码。取消匿名试用。这些功能与安全边界须在重构版继续实现并回归验证。

当前在线服务为模块化单体，业务状态和权限在同一个 PostgreSQL 事务内更新。独立离线模式在 Android 的 SQLite 上使用相同精确领域规则；云端绑定设备保存本机投影和原待办。接口经分层依赖保持可替换，不为单店拆出跨库资金事务。

## 数据与并发事实

在线会员资料、账户、期初、流水、成交、配置、身份、授权、回执和审计均使用明确关系表。金额使用整数分；API 不挂业务数据库卷，不落本地业务归档。旧表和 v1 回放不参加运行，遇旧账表会拒绝迁移。

单笔资金控制目标会员账户版本及短行锁，提交同店变更水位仍有短协调锁。按服务端键分页，报表由 SQL 聚合。普通任务和批次使用独立任务号和版本，恢复持排他门店锁并创建新代际。SQLite 用原生数据库事务，在确认前写余额、流水、回执、审计及 outbox；Android 桥将 64 位值以文本编码。具体压测预算及证据另见测试计划，不能由结构推断吞吐。

## 信任边界

- 商家：账本用 /api/v2，身份、设备、语音等继续用 /api/v1；租户从有效会话取得，写请求的捕获身份必须匹配。
- 平台 API：/api/platform/v1，独立账户、令牌表、角色权限表。平台令牌不能用于商家接口，反之亦然。
- 原生离线：Android 安全存储保存授权及登录凭据；账本备份不含授权。离线许可证绑定设备，使用 ECDSA P-256 / SHA-256 公钥验签，客户端不含签发私钥。
- 在线授权：请求和资金事务重新核验门店状态、用户状态、许可证及功能。服务端返回受商业授权和设备策略共同约束的离线租期。

完全离线设备无法收到远程禁用；期限依靠签名到期时间、持久化时间水位和单调时钟检查。系统重装、Root、修改程序及回滚完整设备状态无法靠纯离线软件完全防御。若业务要求可靠远程撤销或可信计时，应选择在线授权且 offlineHours=0，或使用硬件安全模块/可信时钟。

## 可用性与容量规划

默认 Compose 运行单 API 与反向代理，连接外部 PostgreSQL；未提供自动故障切换。API 无进程内业务会话，令牌、权限与登录限流在数据库中，允许部署多个 API 副本。HTTP 的并发/频率保护是每实例限制，需要在负载均衡器统一限流；共享数据库的登录限制仍然有效。数据库连接池总量应按 API 副本数计算并留运维余量，可在前方使用 PgBouncer transaction pooling；不能依赖本进程内存进行权限撤销。

当前单店不要求实施多 API、分库或集群，先使用独立数据库服务、可恢复备份、资源边界和监控。未来有节点故障持续服务需求时，再实施多可用区主备、流复制、自动故障转移管理器、稳定读写入口和负载均衡。故障切换必须有 fencing 防止双主。异步复制存在 RPO；同步复制增加提交延迟且在同步节点不可达时可能阻塞。根据可接受的 RPO/RTO 选择并演练，不能只加一个副本就宣称零丢失。

备份应包含加密的全量备份、连续 WAL 归档、离线备份副本、授权签名密钥和恢复演练。数据库主备不能替代备份。不要把主备共享同一块磁盘作为灾备。分库分片前先用增长数据核验 SQL、索引和连接池；按 store_id 分片时须设计平台跨店查询与迁移路由，跨店统计可异步汇总。
