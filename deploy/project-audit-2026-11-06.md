## 1. [P1] 手机放弃本机待办后，迟到的原请求仍能入账

位置：[`src/cloud-client.js:312`](../src/cloud-client.js#L312)，尤其是 `useCloudLedger()` 在读取远端后直接清空 `outbox` 的部分；界面确认文案在 `src/components/CloudSettings.vue` 的 `useCloud()`。

触发过程：

1. 云端会员余额 100 元，手机本机扣款 10 元并发送同步请求。
2. 网络中断或请求超时，手机无法确认原请求结果，保留原操作单号。
3. 用户选择“确认放弃本机尚未同步的变更，改用云端账本”。远端读取此时仍为 100 元，本机恢复到 100 元并清空待办。
4. 原请求迟到后仍可通过 `/sync` 成功提交，云端余额变为 90 元。后续拉取又会带回用户以为已放弃的扣款。

原因：清空本机队列没有撤销原请求的服务端写入资格。读取账本也没有为未入账操作登记取消记录。HTTP 断开或客户端 AbortController 不会自动撤销服务端正在等待或处理的财务事务。

证据：`node output/project-audit/reproduce.mjs` 在临时 PGlite 数据库和本机 HTTP API 上验证：采用云端后的本机余额为 `10000` 分、待办数为 0；随后向真实 HTTP API 交付原请求，返回 200，云端余额为 `9000` 分。脚本用可控传输失败模拟原请求迟到，没有连接生产环境或声称已执行真实 PostgreSQL 并发测试。

建议：覆盖本机前保留恢复点，暂停新增财务写入，并逐批在服务端账本锁内核对原操作。已入账的保留，未入账的登记持久取消记录；全部核对成功后才采用返回的账本并清空队列。普通待办可复用 `server/service.js` 的 `resolveOperations()`；恢复类大请求和初始化操作还需对应容量及取消语义。核对响应丢失时必须重试同一次核对，不能直接丢弃单号。PC 的 `AdminApiClient.resolvePending()` 已实现可参考的流程。

## 2. [P2] 手机消费、充值确认没有重新核对会员身份资料

位置：[`src/composables/useConsume.js:141`](../src/composables/useConsume.js#L141)、[`src/composables/useRecharge.js:124`](../src/composables/useRecharge.js#L124)。

确认页打开后，另一设备更正同一档案的姓名或手机号，且余额不变。同步带回最新资料后，消费和充值确认函数只检查余额；确认框仍显示旧姓名，写入却使用最新档案，成功反馈和充值通知还会采用旧姓名。

证据：`node output/project-audit/reproduce-ui.mjs` 分别调用真实消费、充值 composable：确认页显示“张三”，随后将档案改为“李四”和另一手机号，直接确认仍成功，最新流水记录“李四”的新资料。没有要求用户再次核对。

建议：确认时固定会员 ID、姓名、手机号、余额及注销状态，提交前比较该快照；任何用于确认身份的字段变化都重建确认页。消费端已经保存 `memberPhone`，但没有比较；充值端需要同时保存该字段。成功文案与回执应使用最终确认的身份。

## 3. [P2] PC 充值播报可能使用过期余额

位置：[`admin/src/views/MembersView.vue:463`](../admin/src/views/MembersView.vue#L463) 至充值成功后的播报调用。

充值弹窗持有打开时的会员对象。弹窗保留期间账本重新加载，例如锁屏后解锁加载最新账本，父组件传入新会员数组，弹窗引用仍是旧对象。构建操作时使用新的 `adminApi.accountData`，因此入账可能成功；播报却使用旧余额自行相加，并丢弃 `submitOperation()` 的确认结果。

证据：UI 复现中，弹窗初始余额为 100 元，账本更新为 150 元，随后实充 10 元、赠送 1 元。提交操作的前置条件为 150 元，确认结果为 161 元，实际传给播放器的余额为 `111.00`。

建议：使用服务端确认结果中对应会员及流水的实际结果构造播报，避免从弹窗缓存推算余额；加载后的会员资料也应更新或重新核对弹窗。

## 4. [P2] PC 充值播报遗漏设置页支持的赠送变量

位置：[`admin/src/views/MembersView.vue:476`](../admin/src/views/MembersView.vue#L476)；设置页声明变量在 [`src/components/VoiceSettings.vue:291`](../src/components/VoiceSettings.vue#L291)。

共享设置页允许充值语句使用 `{gift}` 和 `{totalCredit}`，App 已传入这两个字段，PC 充值成功后只传入 `name`、`amount`、`balance`。播放器对缺失变量保留原占位符，导致保存的合法语句无法完整播报。

证据：上述 UI 复现捕获真实 PC 充值播报参数，再用实际 `VoicePlayer.formatTemplate()` 格式化“赠送 {gift} 元，到账 {totalCredit} 元”，两处占位符仍保留。

建议：PC 充值播报传入两位小数的实际赠送金额和实际合计入账金额，并覆盖从 PC 提交到最终合成文本的完整路径。

## 5. [P3] 天猫精灵将已撤销消费作为最近到店记录

位置：[`server/aligenie.js:605`](../server/aligenie.js#L605)。

查询余额时，最近消费筛选仅检查会员 ID 和 `CONSUME` 类型，没有排除 `isRefunded`。错误扣款随后冲正，即使会员没有任何有效消费，仍会播报该错误交易的日期为上次到店。

证据：`reproduce.mjs` 建立有效的充值、消费、冲正历史，确认未撤销消费数量为 0；通过已签名、设备已绑定的真实 webhook 查询，仍返回“上次到店是 今天”。

建议：筛选未撤销消费；无有效消费时省略到店日期，与客户列表的统计口径一致。
