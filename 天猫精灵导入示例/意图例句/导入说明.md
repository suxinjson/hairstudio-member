# 天猫精灵模板语料导入

查询、充值、消费三个业务意图全部采用参数模板，主文件和补充文件在各意图内去重。姓名、手机尾号、完整手机号、金额和服务名称均由参数提供，不在业务语料中写死具体取值。

CSV 保持平台示例格式：GBK 编码、分号分隔、每个字段使用双引号、第一行是列名。模板的参数值列留空。`corpus_sample.csv` 是原始格式参考。DefaultWelcomeIntent 没有业务参数，欢迎语料继续使用技能呼叫表达；当前呼叫名为“顾客”时，在平台唤醒配置中使用实际呼叫名。

| 意图 | 文件 | 模板数 |
| --- | --- | ---: |
| QueryMemberIntent | 002_QueryMemberIntent.csv | 24 |
| QueryMemberIntent | 002_QueryMemberIntent_补充.csv | 8 |
| RechargeIntent | 003_RechargeIntent.csv | 20 |
| ConsumeIntent | 004_ConsumeIntent.csv | 25 |
| ConsumeIntent | 004_ConsumeIntent_补充.csv | 10 |

共 87 条业务模板：查询 32 条、充值 20 条、消费 35 条。

## 模板怎样匹配会员和金额

消费模板 `@{memberQuery}消费@{amount}` 可以复用于关联会员实体中的不同姓名或号码，以及金额实体识别的不同金额，无需为每一位会员新增完整句。查询模板是 `查询@{memberQuery}余额`，充值模板是 `@{memberQuery}充值@{amount}`；带服务项目的消费模板是 `@{memberQuery}@{service}扣款@{amount}`。

具体例句不一定只匹配固定文字：如果其中的姓名、金额、服务词段已绑定参数，也可以根据关联实体泛化；未绑定的文字才按固定表达匹配。统一成模板可以明确哪些部分是变量，并减少重复姓名例句。

**模板不会自动接受任意姓名，也不会同步后端会员库。** `memberQuery` 的识别范围仍取决于平台关联的会员实体、模型构建和识别效果。必须先录入门店真实姓名、实际手机尾号或完整手机号。新增会员时继续维护同一个会员实体，不需要重复新增消费、充值和查询语料。姓名同音或误识别需要核对后才配置同义词，不能把苏鑫、苏新、舒心、租心直接当成同一位会员。

金额模板使用 `@{amount}`，参数关联 sys.price，测试说“一百元”“200.50元”“两百块钱”等带单位的金额。不要把整段姓名或金额改成普通文字，也不要为参数设置默认会员或默认金额。memberQuery 不要直接换成 sys.select；该实体需要后端提供动态候选选择流程，当前接口没有实现这套流程。

## 先配置实体和参数，再导入

CSV 表头、占位符和空参数列是语料格式，不会自动创建意图参数、配置追问或填充会员实体。先在平台“语音交互模型 → 实体”维护会员实体、引用公共金额实体 sys.price，并建立门店服务实体。

| 意图 | 参数 | 关联实体 | 必选 |
| --- | --- | --- | --- |
| QueryMemberIntent | memberQuery | 会员标识 member_entity | 是 |
| RechargeIntent | memberQuery | 同一个会员实体 | 是 |
| RechargeIntent | amount | sys.price | 是 |
| ConsumeIntent | memberQuery | 同一个会员实体 | 是 |
| ConsumeIntent | amount | sys.price | 是 |
| ConsumeIntent | service | 服务品项 service_item | 否 |

查询、充值、消费复用同一个会员实体；服务实体包含门店实际项目及经过核对的同义说法。service 非必选，不填虚构服务默认值，没说服务的句子使用不带 `@{service}` 的模板。

平台“实体列表”中的实体名称、实体标识与“意图 → 参数”中的参数名称是不同字段。当前实体标识为 member_entity、service_item、sys.price；本套 CSV 的参数名称为 memberQuery、service、amount，所以占位符分别写 `@{memberQuery}`、`@{service}`、`@{amount}`。在意图中按上表关联即可，不需要把占位符改成实体标识。若实际使用了不同参数名称，CSV 表头、模板占位符和追问回复必须一起按该参数名称调整。

1. 在对应意图建立上表参数，核对名称和大小写，保存实体及参数配置。
2. 在每个意图的**单轮用户表达/语料**中导入对应文件。查询、消费各自同时使用主文件和补充文件；充值使用主文件。
3. 检查 `@{memberQuery}消费@{amount}` 中两个占位符确实关联 memberQuery 和 amount，不能仅凭文字显示或高亮颜色判断。
4. 配置下方的参数追问，然后保存并执行平台训练/构建。
5. 构建成功后开启新的网页测试会话，先核对意图和槽值，再开启真机测试并验证已绑定音箱。

平台已有旧语料时，先导出留存，再清理重复模板和写死姓名、金额的旧业务句，使用对应的模板文件替换；若已有相同模板，只保留一条。实体值、意图参数、服务接口和技能呼叫名是独立配置，换语料时继续保留正确配置。本地 CSV 改动必须导入平台并重新构建后才会生效，无需为了更换语料修改后端接口。

## 手机号被识别成金额

如果“完整手机号消费100”返回 ConsumeIntent、amount 却是手机号，而加“100元”后 amount 正确但仍追问会员，说明金额已能识别，会员标识仍未填入。单独回答手机号又变成意图 null，进一步指向会员实体取值、参数关联或追问回复未命中；仅凭这些结果不能确认具体是哪一项配置未生效。

1. 核对 ConsumeIntent 的 memberQuery 关联 member_entity，amount 关联 sys.price。实体列表中存在 sys.anyNumber 不表示 memberQuery 已关联它；当前模板中金额使用价格实体，会员数字仍需按会员实体配置识别。
2. 在 member_entity 的**实体值**中检查并录入真实完整手机号、实际手机尾号。只录入姓名不会自动补出这个会员的号码。号码应能在后端找到实际会员；尾号保留前导零。对逐位中文读法，先核对平台识别原文，再为同一个号码维护正确的同义说法。
3. 查询、消费、充值复用这个实体。会员参数的“用户可能回复”配置 `@{memberQuery}`、`手机号@{memberQuery}`、`尾号@{memberQuery}`、`手机尾号@{memberQuery}`，然后保存并重新构建模型。
4. 先测试“查询手机号〔实际完整号码〕余额”，再测试“手机号〔实际完整号码〕消费一百元”。方括号是说明，测试时替换成实际号码。补充文件已包含 `查询手机号@{memberQuery}余额`、`手机号@{memberQuery}消费@{amount}`、`电话@{memberQuery}消费@{amount}`、`尾号@{memberQuery}消费@{amount}`；这些前缀帮助区分标识与金额，但仍需会员实体实际识别该号码。
5. 验收时会员号码应填入 memberQuery，消费金额应填入 amount；出现 amount=手机号时先修正平台识别，不进入确认操作。测试金额完整说“100元”或“一百元”，避免两个无单位数字竞争参数。

后端金额解析新增对无单位完整手机号格式的拒绝；即使平台误把手机号放入 amount，也不能据此创建待确认消费或充值。该处理不会把错槽自动改成会员槽，需要更新 API 后生效。平台尚未补齐必选会员时可能不调用后端，因此仍须修复平台实体、追问和模型。

## 参数追问也使用模板

在相应**意图 → 参数 → 精灵追问**中，分别配置追问文案与“用户可能回复”；不能只把这些回复放在单轮用户表达中。

| 意图 / 参数 | 精灵追问 | 用户可能回复模板 |
| --- | --- | --- |
| 查询 / memberQuery | 请说会员姓名、手机号或手机尾号 | `@{memberQuery}`、`会员@{memberQuery}`、`手机号@{memberQuery}`、`尾号@{memberQuery}`、`手机尾号@{memberQuery}` |
| 消费 / memberQuery | 请说扣款会员姓名、手机号或手机尾号 | `@{memberQuery}`、`会员@{memberQuery}`、`手机号@{memberQuery}`、`尾号@{memberQuery}`、`手机尾号@{memberQuery}` |
| 消费 / amount | 请说消费金额，例如一百元 | `@{amount}`、`消费@{amount}` |
| 充值 / memberQuery | 请说充值会员姓名、手机号或手机尾号 | `@{memberQuery}`、`会员@{memberQuery}`、`手机号@{memberQuery}`、`尾号@{memberQuery}`、`手机尾号@{memberQuery}` |
| 充值 / amount | 请说充值金额，例如两百元 | `@{amount}`、`充值@{amount}` |

消费补充文件包含 `消费@{amount}` 和 `@{memberQuery}消费`，供测试缺少会员或金额的入口。参数必选及追问配置只在已识别该意图后起作用，不会把欢迎后的任意姓名、数字自动解释为消费或充值。欢迎后先说完整业务指令；已经追问 memberQuery 时才单独报姓名或号码，已经追问 amount 时回答带“元”的金额。

平台内部的参数追问可能不调用 Webhook；因此只出现追问而没有后端日志时，先查看平台意图、槽值和模型配置。

## 验证与故障定位

以实际已录入会员为例：若姓名是“苏鑫”，测试“苏鑫消费一百元”“苏鑫充值两百元”“查询苏鑫余额”。模板不固定该姓名；换成实体中其他真实会员也应识别。手机号和尾号需使用实际已录入实体的值。

| 测试结果 | 下一步 |
| --- | --- |
| 完整句命中 ConsumeIntent，首轮同时返回 memberQuery 和 amount | 继续验证后端回复和确认流程 |
| 意图正确，参数为 null 或只有 amount | 核对模板参数绑定、关联实体和构建版本；再测试追问回复 |
| UNKNOWN_DOMAIN / 未进入技能 | 先核对当前测试技能、会员实体、单轮模板及构建版本；该轮后端无法处理 |
| 网页文字测试命中，音箱跳出技能或解释姓名词义 | 核对平台识别原文、会员实体同义词、真机测试权限和欢迎后开麦时机 |
| 未在会员库中找到姓名 | 请求已到后端，核对当前门店真实会员及注销状态；实体值不会创建会员 |
| 服务开小差 | 对照平台 HTTP 调用结果及同一时间的 aligenie.request / rejected / response，不能只凭兜底提示推断原因 |

网页测试先验证意图和参数。缺少真实用户/设备标识时，后端只提供在线测试引导，不执行真实记账。音箱测试先开启当前账号/设备的真机测试权限，并在系统中绑定真实音箱。说“天猫精灵，打开顾客”，听到“梦飞空间欢迎您，请说”后等待自动开麦，再说完整业务指令。

消费、充值在播报会员、金额及余额后回答“是的”才确认。只有收到成功回复后才核对对应流水；业务响应结束技能会话后，下一笔重新唤起。欢迎成功不代表消费已完成，也不代表后续每一句都能进入技能。

后端诊断日志、设备绑定、签名配置和业务错误提示见[语音服务说明](../../deploy/voice-integration.md)。在服务器项目目录读取近期测试日志：

```bash
bash deploy/read-aligenie-logs.sh --since 30m --tail 200
```
